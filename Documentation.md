# Graylog SIEM Home Lab — Documentation

## Overview

This project documents the deployment of a small Security Information and Event Management (SIEM) environment using Graylog and NXLog.

The purpose of the project was to gain hands-on experience with centralized logging, Windows event analysis, Linux administration, networking, log collection, and security monitoring.

The SIEM currently monitors a single Windows PC, with Graylog running on a Kali Linux virtual machine.

---

# Environment

The SIEM consists of two primary systems:

| System | Role |
|---|---|
| Windows PC | Log source |
| Kali Linux VM | Graylog SIEM server |

Additional software:

| Software | Purpose |
|---|---|
| Graylog | SIEM and centralized log management |
| NXLog | Windows log collection and forwarding |
| VirtualBox | Virtualization and networking |
| Windows Event Viewer | Windows event investigation |
| PowerShell | Windows administration and troubleshooting |

# Project Goals

The main goals of this project were to:

- Learn how a SIEM works
- Deploy Graylog in a Linux environment
- Collect Windows event logs
- Forward logs from Windows to Graylog
- Search and analyze collected events
- Build basic SIEM dashboards
- Investigate Windows events
- Practice troubleshooting a multi-component logging system

---

# Graylog Server

Graylog was deployed on the Kali Linux virtual machine.

Graylog is responsible for:

- Receiving log data
- Storing and indexing messages
- Searching collected events
- Filtering log data
- Creating visualizations
- Building dashboards

The Graylog environment provides a centralized location for investigating activity generated by the Windows system.

---

# Windows Log Source

The Windows PC acts as the primary log source.

Windows generates different types of events, including system, application, and security-related events.

Windows Event Viewer was used to inspect events directly on the Windows system before investigating the same information through Graylog.

---

# NXLog

NXLog was used as the log collection and forwarding agent on Windows.

The basic log flow is:

```text
Windows Event Logs
        ↓
      NXLog
        ↓
Network Connection
        ↓
Kali Linux
        ↓
     Graylog
```

NXLog collects Windows event information and forwards it to the Graylog server.

---

# Log Collection

The logging pipeline was tested to verify that events could travel from Windows to Graylog.

The major components were:

1. Windows event generation
2. NXLog collection
3. Network communication
4. Graylog input
5. Graylog message ingestion
6. Log searching
7. Dashboard visualization

Each stage was investigated independently when troubleshooting problems.

---

# Windows Event Investigation

Windows Event Viewer was used to investigate events generated by the operating system.

Event IDs were used to identify specific types of activity.

One event encountered during the project was:

```text
Event ID 5379
```

An ActivityID was also encountered during event investigation.

The purpose of examining events in Windows Event Viewer was to understand the original event before attempting to search for and analyze it within Graylog.

---

# Graylog Searching

After logs were successfully collected, Graylog's search functionality was used to investigate Windows events.

The search process involved examining:

- Event IDs
- Timestamps
- Event fields
- Event messages
- Available metadata

One challenge was determining which fields were actually available in the ingested messages.

This demonstrated the importance of inspecting the structure of incoming logs before creating searches and filters.

---

# Dashboard

A Graylog dashboard was created to provide a visual overview of collected Windows activity.

The dashboard was used to practice:

- Creating visualizations
- Filtering events
- Aggregating log data
- Identifying useful monitoring information
- Organizing SIEM information

Because the current environment monitors only one Windows system, some multi-source visualizations have limited usefulness.

For example, a "Top Sources" visualization is less valuable when there is only one log source.

---

# Security Monitoring

The SIEM was used as a learning environment for investigating Windows activity.

Areas explored included:

- Windows security events
- Authentication-related events
- Credential-related events
- System activity
- Event IDs
- Event metadata

The project focused on learning how to collect and investigate events rather than building a production security monitoring environment.

# Troubleshooting Methodology

The SIEM troubleshooting process developed into a layered approach:

```text
Windows Event Generation
          ↓
        NXLog
          ↓
       Network
          ↓
    Graylog Input
          ↓
   Message Ingestion
          ↓
      Log Fields
          ↓
       Searches
          ↓
      Dashboards
```

When a problem occurred, each stage was investigated independently.

# Lessons Learned

A major lesson from this project was that troubleshooting a SIEM requires understanding the entire logging pipeline.

A problem with missing events could originate from:

- Windows
- NXLog
- Network connectivity
- Firewall configuration
- Graylog inputs
- Log processing
- Search configuration
- Dashboard configuration

Each component can be tested independently to isolate problems.
